\section{User interface}

\subsection{Keyword overview}

QConnectBase contains the following keywords:

\begin{itemize}
   \item \rcode{connect}\\
         \textit{Establishes a connection to a specified host.}
   \item \rcode{disconnect}\\
         \textit{Terminates the connection to a host.}
   \item \rcode{send_command}\\
         \textit{Sends a command to the connected host.}
   \item \rcode{verify}\\
         \textit{Verifies the answer received from the connected host. Optionally sends a command (usually to trigger the answer).}
   \item \rcode{transfer_item}\\
         \textit{Sends an item to the connected host. Receives items from the connected host also.}
   \item \rcode{transfer_file}\\
         \textit{Deprecated: Use \rcode{transfer_item} instead!}
\end{itemize}

\subsection{Library import}

The keywords can be accessed with the following library import:

\begin{robotcode}
Library    QConnectBase.ConnectionManager    AS    conn_manager
\end{robotcode}

\textit{We recommend to shorten the QConnectBase library name by using the \rcode{AS} statement.}

\subsection{Usecases}

\textbf{QConnectBase} supports various types of connections. This results in different \rcode{connect} parameters.
The following examples refer to the connection type \rcode{TCPIPClient}.

The \rcode{connect} parameters for the connection type \rcode{TCPIPClient} are defined as follows:

\begin{robotcode}
*** Variables ***

${HOST}=    localhost
${PORT}=    ${1234}

&{TCPIPClientParams}    conn_type=TCPIPClient
...                     address=${HOST}
...                     port=${PORT}
...                     logfile=./tcp_ip_incoming.log
\end{robotcode}

The logfile parameter is optional. It contains the path and the name of a file in which \textbf{QConnectBase}
logs all incoming messages.

\noindent\centerline{\rule{0.2\linewidth}{0.4pt} \large $\star$ \normalsize \rule{0.2\linewidth}{0.4pt}}

\subsubsection{Connect to a host}

Required are a name of the connection together with the connection parameters.

\begin{robotcode}
conn_manager.connect    conn_name=my_test_connection
...                     conn_conf=${TCPIPClientParams}
\end{robotcode}

In case of errors, \textbf{QConnectBase} terminates the test execution. If you want to keep full control over
the test flow, you'll need to use the Robot Framework BuiltIn keyword \rcode{run_keyword_and_ignore_error}
(\textit{the same for all other keywords also}).

\begin{robotcode}
${status}    ${result}=    run_keyword_and_ignore_error    conn_manager.connect    conn_name=my_test_connection
                                                           ...                     conn_conf=${TCPIPClientParams}
\end{robotcode}

\rcode{status} can be one of \rcode{PASS}, \rcode{FAIL}. \rcode{result} is either \rcode{None} or contains
an error message.

\subsubsection{Verify an answer}

\textit{Verify an answer received from connected host. Optionally send a command (usually to trigger the answer).}

\rcode{verify} distinguishes between the verification of a single incoming message and a block of several incoming messages.
The verification occurs by checking whether an incoming message or a block of messages matches one or more than one pattern.
\rcode{verify} patterns are regular expressions. Several different patterns are supported. Some allow matching groups,
while others do not.

\vspace{2ex}

This results in the following possibilities:

\begin{enumerate}
    \item Verify a single incoming message.
    \begin{enumerate}
        \item The pattern does not contain matching groups:\\
        \textit{In case of a match, \rcode{verify} returns \rcode{PASS} (but not the entire message), otherwise \rcode{FAIL}.}
        \item The pattern contain one or more than one matching group:\\
        \textit{In case of a match, \rcode{verify} returns a list of substrings captured from the incoming message, otherwise \rcode{None}.}
    \end{enumerate}
    \item Verify a block of several incoming messages.\\
        In case of a block is verified, the pattern is interpreted as \textit{multiline} pattern by the regex engine.
        This multiline pattern is applied to all messages of the block \textbf{in one single step}.
        This means: No iteration of a list of messages happens!
    \begin{enumerate}
        \item The pattern does not contain matching groups:\\
        \textit{In case of a match, \rcode{verify} returns \rcode{PASS} (but not the entire block of messages), otherwise \rcode{FAIL}.}
        \item The pattern contain one or more than one matching group:\\
        \textit{In case of a match, \rcode{verify} returns a list of substrings captured from the entire block of messages, otherwise \rcode{None}.}
    \end{enumerate}
\end{enumerate}

\vspace{2ex}

The \rcode{verify} keyword has the following prototype:

\begin{robotcode}
verify    conn_name      <\textless{} the name of the connection \textgreater{}>
          search_pattern <\textless{} the regular expression used to verify the message(s) \textgreater{}>
          timeout        <\textless{} timeout while waiting for messages within a match\_try \textgreater{}>
          match_try      <\textless{} number of attempts to match the search\_pattern \textgreater{}>
          fetch_block    <\textless{} whether to wait for a single message or for a block \textgreater{}>
          eob_pattern    <\textless{} pattern to define the end of a block \textgreater{}>
          filter_pattern <\textless{} pattern to make a preselection of block messages \textgreater{}>
          send_cmd       <\textless{} command sent to the connected host \textgreater{}>
          kwargs         <\textless{} additional parameter \textgreater{}>
\end{robotcode}

\vspace{2ex}

The boolean parameter \rcode{fetch_block} is the main switch to distinguish between waiting for a single message
or for a block of messages. The default is \rcode{False} (= wait for a single message only).

The regex parameter \rcode{search_pattern}
\begin{itemize}
   \item decides if the received message is the desired one or not (if \rcode{fetch_block} is \rcode{False}),
   \item decides if all received messages of a block are the desired ones or not (if \rcode{fetch_block} is \rcode{True}).
\end{itemize}

\rcode{verify} waits within \rcode{timeout} \rcode{match_try} times. Every single \rcode{match_try} causes \rcode{verify}
to send \rcode{send_cmd} again (if defined).

\newpage

\textit{Block detection}

A block is a list of incoming messages and is used if a certain pattern (the \rcode{search_pattern}) is not expected to match a single message only but
several messages instead. Therefore, the \rcode{search_pattern} is a multiline pattern.

A block of messages has a begin and an end.
\begin{itemize}
   \item The block detection starts with the execution of the \rcode{verify} keyword (= \textit{moment in time})
   \item The block detection ends when an incoming message matches a pattern named \rcode{eob_pattern} (= \textit{event driven}).
\end{itemize}

Like the \rcode{search_pattern}, the \rcode{eob_pattern} is a regular expression - but must not contain matching groups. It's a simple
yes/no decision. The \rcode{eob_pattern} does not extract any content.

All messages belonging to a block, are stored within an internal message queue intermediately. After the block is detected (match of \rcode{eob_pattern}),
the list of messages within this queue is converted to a single string with hard coded line ending characters (\rcode{\\r\\n}).
\begin{robotcode}
"message1\r\nmessage2\r\nmessage3\r\nmessage4"
\end{robotcode}
And exactly this is finally the string on which the \rcode{search_pattern} is applied.

\vspace{2ex}

\textit{Preselection of incoming messages}

Up to now, we have assumed that during block detection, every incoming message is temporarily stored in the message queue.
But that doesn’t necessarily have to be the case.
If many of the incoming messages are irrelevant for later content analysis, it is possible to place a filter in front
that only allows messages with the desired content to pass through.

This filter is called \rcode{filter_pattern}. Optionally this filter can be used to make a preselection of messages.
If the \rcode{filter_pattern} is not defined, all incoming messages will be accepted and stored in the message queue.

Like the \rcode{eob_pattern}, the \rcode{filter_pattern} is a regular expression - and must also not contain matching groups. It's a simple
yes/no decision. The \rcode{filter_pattern} does not extract any content.

\vspace{2ex}

\textbf{Consider: If you use backslashes within regular expressions defined in Robot Framework code, you have to mask the backslashes:} \rcode{\\\\}!

\vspace{2ex}

A full description of the keyword interface can be found \hyperref[qconnectbase-connection-manager-connectionmanager-verify]{here}.

\section{Verify examples}

Because the \rcode{verify} keyword provides a lot of parameters, this section contains some examples that demonstrate the usage.

\subsection{Verify a single message (1)}

\textit{Verify a single message without matching groups.}

\vspace{2ex}

\textit{Use case}:
\begin{itemize}
   \item Outgoing message: \rlog{TEST-MESSAGE}
   \item Received message: \rlog{TEST-MESSAGE ACK}
   \item \rcode{fetch_block} is \rcode{False} (\textit{default})
   \item No matching groups within the \rcode{search_pattern}
   \item \rcode{search_pattern} matches the received message
\end{itemize}

\textit{Code}:
\begin{robotcode}
${result}=    conn_manager.verify    conn_name=TEST-CONNECTION
              ...                    search_pattern=TEST-MESSAGE\\sACK
              ...                    send_cmd=TEST-MESSAGE
\end{robotcode}

\textbf{Consider: In Robot Framework code, backslashes need to be masked:} \rcode{\\\\}!

\textit{Result}:

Because the \rcode{search_pattern} does not contain matching groups, the result is \rcode{None}.

\begin{robotlog}
INFO - Search pattern 'TEST-MESSAGE\sACK' matched (try 1) on connection 'TEST-CONNECTION'
INFO - ${result} = None
\end{robotlog}

\noindent\centerline{\rule{0.2\linewidth}{0.4pt} \large $\star$ \normalsize \rule{0.2\linewidth}{0.4pt}}

\subsection{Verify a single message (2)}

\textit{Verify a single message with matching groups.}

\vspace{2ex}

\textit{Use case}:
\begin{itemize}
   \item Outgoing message: \rlog{TEST-MESSAGE-1}
   \item Received message: \rlog{TEST-MESSAGE-1 ACK}
   \item \rcode{fetch_block} is \rcode{False} (\textit{default})
   \item \rcode{search_pattern} contains matching groups
   \item \rcode{search_pattern} matches the received message
\end{itemize}

\textit{Code}:
\begin{robotcode}
conn_manager.verify    conn_name=TEST-CONNECTION
...                    search_pattern=TEST-MESSAGE-(\\d)\\s(\\w+)
...                    send_cmd=TEST-MESSAGE-1
\end{robotcode}

\newpage

\textit{Result}:

Because \rcode{search_pattern} contains matching groups, the result is a list containing the captured substrings
from incoming message.

\begin{robotlog}
INFO - Search pattern 'TEST-MESSAGE-(\d)\s(\w+)' matched (try 1) on connection 'TEST-CONNECTION'
INFO - ${result} = ['1', 'ACK']
\end{robotlog}

The result list can be iterated as follows:
\begin{robotcode}
FOR    ${element}    IN    @{result}
    log    element: '${element}'
END
\end{robotcode}

\noindent\centerline{\rule{0.2\linewidth}{0.4pt} \large $\star$ \normalsize \rule{0.2\linewidth}{0.4pt}}

\subsection{Verify a block of messages (1)}

\textit{Verify a block of messages without filtering and without \rcode{search_pattern}.}

\vspace{2ex}

\textit{Use case}:
\begin{itemize}
   \item Outgoing message: \rlog{FETCHBLOCK-1}
   \item Received list of messages:\\
         \begin{robotlog}
transmission started
transmission point 1 passed
any noise message
transmission point 2 passed
any noise message
transmission point 3 passed
any noise message
transmission ended with code '0'\end{robotlog}
   \item \rcode{fetch_block} is \rcode{True}
   \item No \rcode{filter_pattern} defined
   \item No \rcode{search_pattern} defined
\end{itemize}

\textit{Code}:
\begin{robotcode}
${result}=    conn_manager.verify    conn_name=TEST-CONNECTION
              ...                    eob_pattern=transmission\\sended
              ...                    fetch_block=${True}
              ...                    send_cmd=FETCHBLOCK-1
              ...                    timeout=10
\end{robotcode}

In this example it requires eight seconds to receive all messages that belongs to the block.
Therefore, it is required to define a \rcode{timeout} also (here: 10 seconds). The default value (1 second)
would cause a verify timeout.

\newpage

\textit{Result}:
\begin{itemize}
   \item Because the \rcode{filter_pattern} is not defined, all incoming messages are stored intermediately in the internal message queue.
   \item Because the \rcode{search_pattern} is not defined, the default value ('\rcode{.*}') becomes active. Therefore, we will have a match in every case.
\end{itemize}

\begin{robotlog}
INFO - Search pattern '.*' matched (try 1) on connection 'TEST-CONNECTION'
INFO - ${result} = None
\end{robotlog}

\noindent\centerline{\rule{0.2\linewidth}{0.4pt} \large $\star$ \normalsize \rule{0.2\linewidth}{0.4pt}}

\subsection{Verify a block of messages (2)}

\textit{Verify a block of messages without filtering - but with \rcode{search_pattern} without matching groups.}

\vspace{2ex}

\textit{Use case}:
\begin{itemize}
   \item Outgoing message: \rlog{FETCHBLOCK-1}
   \item Received list of messages:\\
         \begin{robotlog}
transmission started
transmission point 1 passed
any noise message
transmission point 2 passed
any noise message
transmission point 3 passed
any noise message
transmission ended with code '0'\end{robotlog}
   \item \rcode{fetch_block} is \rcode{True}
   \item No \rcode{filter_pattern} defined
   \item No matching groups within the \rcode{search_pattern}
   \item \rcode{search_pattern} matches the received block of messages
\end{itemize}

\textit{Code}:
\begin{robotcode}
${result}=    conn_manager.verify    conn_name=TEST-CONNECTION
              ...                    eob_pattern=transmission\\sended
              ...                    search_pattern=transmission
              ...                    fetch_block=${True}
              ...                    send_cmd=FETCHBLOCK-1
              ...                    timeout=10
\end{robotcode}

\textit{Result}:
\begin{itemize}
   \item Because the \rcode{filter_pattern} is not defined, all incoming messages are stored intermediately in the internal message queue.
   \item Because the \rcode{search_pattern} does not contain matching groups, the result is \rcode{None}.
\end{itemize}

\begin{robotlog}
INFO - Search pattern 'transmission' matched (try 1) on connection 'TEST-CONNECTION'
INFO - ${result} = None
\end{robotlog}

\noindent\centerline{\rule{0.2\linewidth}{0.4pt} \large $\star$ \normalsize \rule{0.2\linewidth}{0.4pt}}

\subsection{Verify a block of messages (3)}

\textit{Verify a block of messages without filtering - but with \rcode{search_pattern} containing matching groups.}

\vspace{2ex}

\textit{Use case}:

\begin{itemize}
   \item Outgoing message: \rlog{FETCHBLOCK-1}
   \item Received list of messages:\\
         \begin{robotlog}
transmission started
transmission point 1 passed
any noise message
transmission point 2 passed
any noise message
transmission point 3 passed
any noise message
transmission ended with code '0'\end{robotlog}
   \item \rcode{fetch_block} is \rcode{True}
   \item No \rcode{filter_pattern} defined
   \item \rcode{search_pattern} contains matching groups
   \item \rcode{search_pattern} matches the received block of messages
\end{itemize}

\textit{Code}:
\begin{robotcode}
${result}=    conn_manager.verify    conn_name=TEST-CONNECTION
              ...                    eob_pattern=transmission\\sended
              ...                    search_pattern=^transmission\\sstarted\\r\\n(.*)\\r\\ntransmission\\sended with\\scode\\s'(\\d+)'
              ...                    fetch_block=${True}
              ...                    send_cmd=FETCHBLOCK-1
              ...                    timeout=10
\end{robotcode}

In this example, the \rcode{search_pattern} is used to capture two parts of the content:
\begin{itemize}
   \item the entire message content between \rcode{transmission started} and \rcode{transmission ended},
   \item the exit code at end of the last message.
\end{itemize}

\textit{Result}:
\begin{itemize}
   \item Because the \rcode{filter_pattern} is not defined, all incoming messages are stored intermediately in the internal message queue.
   \item Because the \rcode{search_pattern} contains matching groups, the result is a list of all captured message parts.
\end{itemize}

\begin{robotlog}
INFO - Search pattern '^transmission\sstarted\r\n(.*)\r\ntransmission\sended\swith\scode\s'(\d+)'' matched (try 1) on connection 'TEST-CONNECTION'
INFO - ${result} = ['transmission point 1 passed\r\nany noise message\r\ntransmission point 2 passed\r\nany noise message\r\ntransmission point 3 passed\r\nany noise message', '0']
\end{robotlog}

\textbf{Remember: The \rcode{search_pattern} is a multiline pattern! Therefore, the first element of the result list is a single string that is a concatenation of all affected messages from
the message queue (with hard coded line endings).}

\noindent\centerline{\rule{0.2\linewidth}{0.4pt} \large $\star$ \normalsize \rule{0.2\linewidth}{0.4pt}}

\subsection{Verify a block of messages (4)}

\textit{Verify a block of messages with \rcode{search_pattern} containing matching groups and with \rcode{filter_pattern} defined.}

\vspace{2ex}

\textit{Use case}:

\begin{itemize}
   \item Outgoing message: \rlog{FETCHBLOCK-1}
   \item Received list of messages:\\
         \begin{robotlog}
transmission started
transmission point 1 passed
any noise message
transmission point 2 passed
any noise message
transmission point 3 passed
any noise message
transmission ended with code '0'\end{robotlog}
   \item \rcode{fetch_block} is \rcode{True}
   \item \rcode{filter_pattern} defined
   \item \rcode{search_pattern} contains matching groups
   \item \rcode{search_pattern} matches the received block of messages
\end{itemize}

\textit{Code}:
\begin{robotcode}
${result}=    conn_manager.verify    conn_name=TEST-CONNECTION
              ...                    eob_pattern=transmission\\sended
              ...                    filter_pattern=transmission
              ...                    search_pattern=^transmission\\sstarted\\r\\n(.*)\\r\\ntransmission\\sended with\\scode\\s'(\\d+)'
              ...                    fetch_block=${True}
              ...                    send_cmd=FETCHBLOCK-1
              ...                    timeout=10
\end{robotcode}

In this example, the \rcode{search_pattern} is used to capture two parts of the content:
\begin{itemize}
   \item the entire message content between \rcode{transmission started} and \rcode{transmission ended},
   \item the exit code at end of the last message.
\end{itemize}

But we only want to have the \rlog{transmission point} messages within our results. We are not interested in all \rlog{noise} messages.
Therefore, we use the \rcode{filter_pattern} to collect the \rlog{transmission} messages only.

\textit{Result}:
\begin{itemize}
   \item Because the \rcode{filter_pattern} is defined, the result only contains messages that matches this filter.
   \item Because the \rcode{search_pattern} contains matching groups, the result is a list of all captured message parts.
\end{itemize}

\begin{robotlog}
INFO - Search pattern '^transmission\sstarted\r\n(.*)\r\ntransmission\sended\swith\scode\s'(\d+)'' matched (try 1) on connection 'TEST-CONNECTION'
INFO - ${result} = ['transmission point 1 passed\r\ntransmission point 2 passed\r\ntransmission point 3 passed', '0']
\end{robotlog}

Now the result only contains the \rlog{transmission point} messages together with the exit code.

\textbf{Remember: The \rcode{search_pattern} is a multiline pattern! Therefore, the first element of the result list is a single string that is a concatenation of all affected messages from
the message queue (with hard coded line endings).}

\hypertarget{description-verify}{%
\subsection{\texorpdfstring{\textbf{verify}}{verify}}\label{description-verify}}

The keyword \rcode{verify} verifies a single message (or several messages) received from the connected server.
Several pattern are available to filter the messages. Optionally, a message can be sent. 

\textbf{Prototype}:

\begin{robotcode}
verify(conn_name:      str,
       search_pattern: str=".*",
       timeout:        int=1,
       match_try:      int=1,
       fetch_block:    bool=False,
       eob_pattern:    str=".*",
       filter_pattern: str=".*",
       send_cmd:       str="",
       kwargs:         dict) -> dict
\end{robotcode}

\textbf{Arguments}:

\begin{itemize}
\item \textbf{conn\_name}:
  \begin{quote}
    Name of the connection.
  \end{quote}

  \item \textbf{send\_cmd}:
  \begin{quote}
    Command to be sent to the other side of connection and waiting for response.

    Default value: empty string \rcode{''}.
  \end{quote}

\item \textbf{search\_pattern}:
  \begin{quote}
    Expectation expressed as a \textbf{regular expression pattern} (more robust than a plain string comparison).
    It will match:
    \begin{itemize}
      \item a single line by default (\rcode{fetch_block} not used)
      \item multiple lines if \rcode{fetch_block} is enabled
    \end{itemize}

    Default value: \rcode{.*}, which means "match any character (\rcode{.}) repeated zero or more times (\rcode{*})".

    In practice, this will always match the response, regardless of its content, unless you specify a stricter pattern.
  \end{quote}

\item \textbf{timeout}:
  \begin{quote}
    Timeout (in seconds) for each \rcode{match_try} (if used) while waiting for the response to match the pattern.

    Default value: \rcode{5}.
  \end{quote}

\item \textbf{match\_try}:
  \begin{quote}
    Number of times to try matching the pattern.

    Default value: \rcode{1}.
  \end{quote}

\item \textbf{fetch\_block}:
  \begin{quote}
    If \rcode{True}, every response line will be put into a block until a line match \rcode{eob_pattern} pattern.

    Default value: \rcode{False}.
  \end{quote}

\item \textbf{eob\_pattern}:
  \begin{quote}
    Applicable only when \rcode{fetch_block} is \rcode{True}.

    Regular expression for matching the endline when using \rcode{fetch_block}.

    Default value: \rcode{.*}.
  \end{quote}

\item \textbf{filter\_pattern}:
  \begin{quote}
    Applicable only when \rcode{fetch_block} is \rcode{True}.

    Regular expression for filtering every line to put into the block of response when using \rcode{fetch_block}.

    Default value: \rcode{.*}.
  \end{quote}

\end{itemize}

\textbf{Return value}:

\begin{quote}
\textbf{A list of captured string from search.}

\textbf{Example}

\begin{robotcode}
${result} = verify  conn_name=SSH_Connection
...                 search_pattern=(?<\textless{}>=\s).*([0-9]..).*(command).$
...                 send_cmd=echo This is the 1st test command.
\end{robotcode}

\begin{itemize}
\tightlist
\item
  \rcode{$\{result\}[0]} will be \rlog{1st},
  i.e.\ the first \emph{captured string} defined in the pattern \rcode{([0-9]..)}.
\item
  \rcode{$\{result\}[1]} will be \rlog{command},
  i.e.\ the second \emph{captured string} defined in the pattern \rcode{(command)}.
\end{itemize}

The \rcode{$\{result\}} can be iterated in \rcode{FOR} loop as below example:
\begin{robotcode}
FOR    ${item}    IN    &{result}
    Log To Console    Captured string: ${item}
END
\end{robotcode}

\hypertarget{description-example}{%
\section{Example}\label{description-example}}

\begin{robotcode}[caption=Robot code example]
*** Settings ***
Documentation    Suite description
Library     QConnectBase.ConnectionManager

*** Test Cases ***
Test SSH Connection
    # Create config for connection.
    ${config_string}=    catenate
    ...  {
    ...   "address": "127.0.0.1",
    ...   "port": 8022,
    ...   "username": "root",
    ...   "password": "",
    ...   "authentication": "password",
    ...   "key_filename": null
    ...  }
    log to console       \nConnecting with configurations:\n${config_string}
    ${config}=             evaluate        json.loads('''${config_string}''')    json

    # Connect to the target with above configurations.
    connect             conn_name=test_ssh
    ...                 conn_type=SSHClient
    ...                 conn_conf=${config}

    # Send command 'cd ..' and 'ls' then wait for the response '.*' pattern.
    send command                conn_name=test_ssh
    ...                         command=cd ..

    ${res}=     Verify        conn_name=${CONNECTION_NAME}
    ...                       send_cmd=echo ~~START~~;ls -la;echo ~~END$?~~\r\n
    ...                       search_pattern=\~\~START\~\~\r\n([\\s\\S]*?)\~\~END(\\d+)\~\~
    ...                       fetch_block=True
    ...                       eob_pattern=^\~\~END(\\d*)\~\~

    Log To Console    ${res}[1]

    # Copy a local file to the SFTP server
    transfer file             conn_name=test_ssh
    ...                       src=${src_put}
    ...                       dest=${dest_put}
    ...                       type=put

    # Copy a remote item from the SFTP server to the local host
    transfer item             conn_name=test_ssh
    ...                       src=${src_get}
    ...                       dest=${dest_get}
    ...                       type=get

    # Disconnect
    disconnect  test_ssh
\end{robotcode}

\textbf{Explanation:}

In the example above, we will establish an SSH connection to the remote host 127.0.0.1:8002 and then navigate back one directory level to list all files/folders within that directory.

To achieve this, we utilize the following steps:

1. First, we use the \rcode{send command} keyword, which is designed to send commands to the server and immediately return without waiting for a response. In this case, we send the command "cd .." to the remote host.

2. Next, we employ the \rcode{verify} keyword, specifically designed for verifying the response from the server after sending a command. The command sent is specified by the \textbf{send\_cmd} argument (here, it is the "ls -la" command). We use a regular expression defined by the \textbf{search\_pattern} argument to verify the response and extract the list of files/folders after executing the "ls -la" command.

However, by default, if no additional arguments are provided, only the first line of the response after running the command will be captured. To address this limitation, we introduce two additional arguments: \textbf{fetch\_block} and \textbf{eob\_pattern}.

When \textbf{fetch\_block} is set to "True", the \rcode{Verify} keyword will capture all lines returned from the server until it encounters a line that matches the pattern defined by \textbf{eob\_pattern} (End of Block pattern). This extended functionality ensures that we can effectively capture multi-line returns from the server.

To handle variable-length output, the \textbf{send\_cmd} parameter encapsulates the command between "START" and "END\$?". By setting \textbf{fetch\_block} to "True" and specifying the \textbf{eob\_pattern}, we can accurately capture the entire list returned by the server between "START" and "END\$?".

\textbf{Example: Verifying service startup logs with \rcode{fetch\_block}}

\textbf{Use case}:
This use case demonstrates how to use \rcode{verify} with \rcode{fetch\_block} and \rcode{eob\_pattern} to monitor the startup of a Linux systemd service.
When restarting a service, the log usually contains multiple lines: some indicate that the service is starting, some show internal information, and finally, one line confirms that the service has been started successfully.
By using \rcode{fetch\_block}, all these lines can be collected into a block until the end-of-block pattern (\rcode{eob\_pattern}) is reached.

\textbf{Command under test}:
\begin{robotcode}
systemctl restart cron; journalctl -u cron --since "now"
\end{robotcode}

\textbf{Sample log output}:
\begin{robotlog}
Sep 12 15:25:01 myhost systemd[1]: Stopping Regular background program processing daemon...
Sep 12 15:25:01 myhost systemd[1]: Starting Regular background program processing daemon...
Sep 12 15:25:01 myhost cron[5678]: (CRON) INFO (pidfile fd = 3)
Sep 12 15:25:01 myhost cron[5678]: (CRON) INFO (Running @reboot jobs)
Sep 12 15:25:01 myhost systemd[1]: Started Regular background program processing daemon.
\end{robotlog}

\textbf{Robot Framework usage}:
\begin{robotcode}
  ${result} = verify  conn_name=SSH_Connection
  ...                 fetch_block=True
  ...                 search_pattern=([^\r\n]*Starting Regular background program processing daemon.*)
  ...                 eob_pattern=.*Started Regular background program processing daemon.*
  ...                 send_cmd=systemctl restart cron; journalctl -u cron --since "now"
\end{robotcode}

\textbf{Returned block}:
\begin{robotlog}
Sep 12 15:25:01 myhost systemd[1]: Starting Regular background program processing daemon...
Sep 12 15:25:01 myhost cron[5678]: (CRON) INFO (pidfile fd = 3)
Sep 12 15:25:01 myhost cron[5678]: (CRON) INFO (Running @reboot jobs)
Sep 12 15:25:01 myhost systemd[1]: Started Regular background program processing daemon.
\end{robotlog}

\textbf{Notes}:
\begin{itemize}
  \item \rcode{search\_pattern} defines the entry point (\emph{Starting...}).
  \item \rcode{eob\_pattern} defines the stopping point (\emph{Started...}).
  \item If the service fails to start (no \emph{Started...} line appears), the keyword will eventually timeout, which makes this a convenient way to verify service startup behavior in automated tests.
\end{itemize}

\textbf{Example: Filtering service startup logs with \rcode{fetch\_block} and \rcode{filter\_pattern}}

\textbf{Use case:}
When a Linux device boots, it sends a large block of startup logs through the connection (e.g., COM port).
We only care about one particular service (``systemd-networkd''). By using \rcode{fetch\_block} together with \rcode{filter\_pattern},
we can extract only the relevant messages. Finally, \rcode{eob\_pattern} is used to stop reading logs as soon as the service reports a successful startup.

\begin{boxhint} {Important Note:}
\rcode{filter\_pattern} filters the incoming lines, keeping only those relevant to the service of interest.

\rcode{eob\_pattern} is applied \textbf{after filtering}, meaning it must match one of the filtered lines.
If it does not, the keyword will not stop until timeout occurs.

This ensures the block stops at the correct line related to the service and avoids including unrelated logs.
\end{boxhint}

\begin{robotcode}
${result} = verify  conn_name=COM_Connection
...                 fetch_block=True
...                 search_pattern=(.*)
...                 filter_pattern=.*systemd-networkd.*
...                 eob_pattern=.*eth0: Gained carrier.*
...                 send_cmd=dmesg --follow
\end{robotcode}

\textbf{Connection log (sample):}
\begin{robotlog}
[    1.234567] systemd[1]: Starting udev Kernel Device Manager...
[    1.456789] systemd[1]: Started udev Kernel Device Manager.
[    2.123456] systemd[1]: Starting Network Service...
[    2.223344] systemd-networkd[120]: eth0: link is up
[    2.223355] systemd-networkd[120]: eth0: Gained carrier
[    2.345678] systemd[1]: Started Network Service.
[    2.456789] systemd[1]: Starting Login Service...
[    2.567890] systemd[1]: Started Login Service.
\end{robotlog}

\textbf{Returned block after applying \rcode{filter\_pattern} and stopping at \rcode{eob\_pattern}:}
\begin{robotlog}
[    2.223344] systemd-networkd[120]: eth0: link is up
[    2.223355] systemd-networkd[120]: eth0: Gained carrier
\end{robotlog}

\textbf{Explanation:}
\begin{itemize}
  \item \rcode{fetch\_block=True} collects all filtered lines until \rcode{eob\_pattern} is matched.
  \item \rcode{filter\_pattern=.*systemd-networkd.*} ensures only logs from the relevant service are included.
  \item \rcode{eob\_pattern=.*eth0: Gained carrier.*} stops collection when the filtered line matches the pattern.
  \item Lines from other services (e.g., udev, Login Service) are automatically excluded from the block.
\end{itemize}

\subsection{Introduction to RMQSignal}
\label{subsec:auxiliary-intro}

The \emph{RMQSignal} class serves as an extension to the core functionalities, providing support for Inter-Process Communication (IPC) based on the RabbitMQ infrastructure. This utility module is designed to facilitate the exchange of signals accompanied by payloads between various processes, enhancing the overall communication mechanism.

\subsection{Library Keywords and Usage}
\label{subsec:keyword-usage}

The keywords provided by this library offer a range of functionalities designed to streamline various tasks and processes. Below are some of the key functionalities along with their usage:

\subsubsection{Send Signal Keyword}
\textbf{Usage}: Used to send a signal to other processes. \\
\textbf{Syntax}: \texttt{Send Signal [signal\_name] [payloads] [Receiver]} \\
\textbf{Arguments}:
\begin{itemize}
    \item \texttt{signal\_name} (string): Defines the name of the signal.
    \item \texttt{payloads}: Specifies the payloads of the signal.
    \item \texttt{Receiver} (optional, default is None): Specifies the receiver. If defined, the signal will be sent only to that specified receiver. If not defined, it sends a broadcast to all receivers.
\end{itemize}

\subsubsection{Wait For Signal Keyword}
\textbf{Usage}: Used to wait for a specific signal within a timeout. \\
\textbf{Syntax}: \texttt{Wait For Signal [signal\_name] [timeout]} \\
\textbf{Arguments}:
\begin{itemize}
    \item \texttt{signal\_name} (string): Defines the name of the signal to wait for.
    \item \texttt{timeout} (optional, default is 10): Specifies the timeout in seconds to wait for the specific signal.
\end{itemize}
\textbf{Return}: Returns the payloads of the received signal, if received within the timeout.

\subsubsection{Wait For Signals Keyword}
\textbf{Usage}: Used to wait for multiple specific signals within a timeout. \\
\textbf{Syntax}: \texttt{Wait For Signals [signal\_names] [timeout]} \\
\textbf{Arguments}:
\begin{itemize}
    \item \texttt{signal\_names} (list of strings): Defines the list of signal names to wait for.
    \item \texttt{timeout} (optional, default is 10): Specifies the timeout in seconds to wait for the full set of specific signals.
\end{itemize}
\textbf{Return}: Returns a list of payloads of the signals in the same order if the full set of signals is received within the timeout.

\subsubsection{Set Signal Receiver Name Keyword}
\textbf{Usage}: Used to set a specific name for the Signal Receiver, which defines a unique name for the current process. Other processes can send signals directly to the current process using this receiver name. \\
\textbf{Syntax}: \texttt{Set Signal Receiver Name [receiver] [force]} \\
\textbf{Arguments}:
\begin{itemize}
    \item \texttt{receiver} (string): Specifies the name to set for the current process signal receiver.
    \item \texttt{force} (optional, default is True): Determines whether to force-create the signal receiver. If \texttt{force} is set to False, an exception will be raised if any process has already defined this name as a signal receiver.
\end{itemize}

\subsubsection{Unset Signal Receiver Name Keyword}
\textbf{Usage}: Used to unset the current Signal Receiver name of the current process. \\
\textbf{Syntax}: \texttt{Unset Signal Receiver Name}

\subsection{Example of Inter-Process Communication}

\textbf{Content of ProcessA.robot file:}
\begin{robotcode}
*** Settings ***
Library        QConnectBase.message.RMQSignal

*** Test Cases ***
Test signal
   Log To Console    Process A start
   Send Signal    HelloFromProcA    Hello, I'm A        receiverB
   Sleep    1s
   Send Signal    Hello2FromProcA    Hello 2nd time, I'm A        receiverB
   ${res}=    Wait For Signal    HelloFromProcB    ${20}
   Log To Console    Get resp signal from ProcB: ${res}
\end{robotcode}

\textbf{Content of ProcessB.robot file:}
\begin{robotcode}
*** Settings ***
Library        QConnectBase.message.RMQSignal

*** Test Cases ***
Receiving Multiple Signals
   Log To Console    message
   Set Signal Receiver Name    receiverB
   ${list_of_signal} =    Create List    HelloFromProcA    Hello2FromProcAfull
   ${res}=    Wait For Signals    ${list_of_signal}    ${15}
   Sleep    2s
   Log To Console    Get signal from ProcA: ${res}
   Send Signal    HelloFromProcB      Hello A, I'm B. Got your signal:${res}
\end{robotcode}

\textbf{Explanation:}
In the above test cases, two separate Robot Framework test files, ProcessA.robot, and ProcessB.robot are used for inter-process communication.

In ProcessB.robot, the test case 'Receiving Multiple Signals' starts by setting up a signal receiver 'receiverB'. It then waits for a set of signals (HelloFromProcA and Hello2FromProcA) from ProcessA. Once both signals are received within 15 seconds, it logs to console the received signals' payloads and waits for 2 seconds before sending a response signal 'HelloFromProcB' to ProcessA.

In ProcessA.robot, the test case 'Sending Multiple Signals' sends HelloFromProcA signal to 'receiverB' in ProcessB. After a 1-second pause, it sends another signal 'Hello2FromProcA' to 'receiverB'. Then, it waits for a response, expecting signal 'HelloFromProcB' from ProcessB within 20 seconds. Upon receiving signal, it logs the received payloads to console.

\section{Contribution Guidelines}\label{description-contribution-guidelines}}

QConnectBaseLibrary is designed for ease of making an extension library.
By that way you can take advantage of the QConnectBaseLibrary's
infrastructure for handling your own connection protocal. For creating
an extension library for QConnectBaseLibrary, please following below
steps.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Create a library package which have the prefix name is
  \textbf{robotframework-qconnect-}\emph{{[}your specific name{]}}.
\item
  Your hadling connection class should be derived from
  \textbf{QConnectBase.connection\_base.ConnectionBase} class.
\item
  In your \emph{Connection Class}, override below attributes and
  methods:
\end{enumerate}

\begin{quote}
\begin{itemize}
\tightlist
\item
  \textbf{\_CONNECTION\_TYPE}: name of your connection type. It will be
  the input of the conn\_type argument when using \textbf{connect}
  keyword. Depend on the type name, the library will detemine the
  correct connection handling class.
\item
  \textbf{\_\_init\_\_(self, \_mode, config)}: in this constructor
  method, you should:
\end{itemize}

\begin{quote}
\begin{itemize}
\item
  Prepare resource for your connection.
\item
  Initialize receiver thread by calling
  \textbf{self.\_init\_thread\_receiver(cls.\_socket\_instance,
  mode="")} method.
\item
  Configure and initialize the lowlevel receiver thread (if it's
  necessary) as below

\begin{verbatim}
self._llrecv_thrd_obj = None
 self._llrecv_thrd_term = threading.Event()
 self._init_thrd_llrecv(cls._socket_instance)
\end{verbatim}
\item
  Incase you use the lowlevel receiver thread for receiving data byte by byte. You should implement the
  \textbf{thrd\_llrecv\_from\_connection\_interface()} method. This
  method is a mediate layer which will receive the data from connection
  at the very beginning, do some process then put them in a queue for
  the \textbf{receiver thread} above getting later.
\item
  Create the queue for this connection (use Queue.Queue).
\end{itemize}
\end{quote}

\begin{itemize}
\tightlist
\item
  \textbf{connect()}: implement the way you use to make your own
  connection protocol.
\item
  \textbf{\_read()}: implement the way to receive data from connection.
\item
  \textbf{\_write()}: implement the way to send data via connection.
\item
  \textbf{disconnect()}: implement the way you use to disconnect your
  own connection protocol.
\item
  \textbf{quit()}: implement the way you use to quit connection and
  clean resource.
\end{itemize}
\end{quote}
